# 0006. Resources counts and progress come from shared sources

Date: 2026-10-22
Status: Proposed

## Context
A review of the Resources feature found that the year and subject pages download every PYQ document (both variants, each with the uploader's name and email populated) just to count papers; PYQ progress is fetched up to three times per visit (`ResourcesPage` calls the hook and ignores it, `YearPage` fetches again, `SubjectPage` keeps its own copy of the hook's logic); and `SubjectPage` makes three list calls on every visit. The year page also shows "0 attempted" on first load because counts are computed before progress arrives. See `ERRORS.md` P1, P2, P3, R3 and R7.

## Decision
- Add `GET /resources/summary` that returns grouped counts per year and subject (an aggregate on the existing `resourceType, year, subject, isActive` index). The year and subject pages use it instead of listing documents.
- Progress has one shared source for all Resources pages (one hook instance, held in a context or a layout route). Attempted counts are derived in render from that source and the summary.
- `SubjectPage` loads the subject once, or loads each tab lazily.
- Resource list and get responses stop populating `uploadedBy`; admin callers keep it if the dashboard needs it.

## Alternatives considered
- Client-side caching of the full lists: rejected, the payload stays large and the uploader data still leaks.
- Pagination: not needed at the current size (128 resources seeded); revisit if content grows.

## Consequences
- One new backend endpoint and one new shared hook or context; the three pages change.
- Counts are exact and cheap, so adding more papers does not slow the first screens.
- If the admin dashboard shows uploader names, it needs its own admin-only call.
